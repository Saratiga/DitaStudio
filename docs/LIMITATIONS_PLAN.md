### 1.2. Условия сборки для `topicref`

- **Где.** `Core/Project/MapTree.cs` — `MapTree.Build` и `PublicationOrder` (фильтр сейчас только по `processing-role`);
  `Core/Publishing/PublishFilter.cs` — готовое правило `IsIncluded(node, options)`; потребители — `HtmlPublisher` (строки 71, 135, 365),
  `DocxPublisher` (77, 108), оглавление и навигация (`TocRules`), предпросмотр карты.
- **Как.** `MapTree.Build(project, mapPath, PublishOptions? options)`: при сборке дерева узел, не прошедший `PublishFilter`, не
  добавляется (вместе с потомками). Без `options` (редактор карты) дерево полное — исключённые строки в редакторе остаются.
  `PublicationOrder` и оглавление работают по уже отфильтрованному дереву. Фильтр применяется и к `reltable` (исключённые топики
  не попадают в «Смотрите также»).
- **Проверки.** Карта из 3 топиков, один `topicref` с `product="a"`; исключение `a` → в HTML-сайте, едином HTML, DOCX и оглавлении
  его нет; без исключения — есть; вложенный `topicref` исключённого `topichead` тоже скрыт; `keydef` с исключённым значением
  остаётся доступным для ключей (ключи не публикуются, но работают); в редакторе карты исключённые строки видны.
- **Риски.** Битые ссылки на исключённый топик из включённых: не считать ошибкой публикации (ссылка снимается с предупреждением в журнале).
- **Документация.** Снять пункт из README; USAGE — раздел «Условия сборки»: исключение действует и на карту.

### 1.3. `.ditaval`: `include` и `passthrough`

- **Где.** `Core/Project/DitavalReader.cs` (читает `prop` с `action` exclude/flag), `DitavalWriter.cs`, модель `DitavalRules`,
  `Core/Publishing/PublishFilter.cs`, диалог «Редактировать .ditaval» (`AvaloniaDialogService.Publishing.cs`).
- **Семантика (DITAVAL 1.3).** `prop att="X" action="exclude"` без `val` — по умолчанию исключить все значения атрибута; затем
  `prop att="X" val="V" action="include"` возвращает значение V. `action="passthrough"` — значение выводится как есть
  (в HTML — как значение атрибута `data-…`/класса, в DOCX игнорируется). `include` без правила по умолчанию ничего не меняет.
- **Проверки.** Чтение и запись всех четырёх действий (круговой обход); исключить всё, вернуть одно значение; сочетание с
  `exclude` по значению; `passthrough` попадает в HTML. Диалог показывает и сохраняет `include`, не теряя правил, которых он не понимает.
- **Документация.** README: убрать «include и passthrough пропускаются»; USAGE — раздел `.ditaval`.

### 1.4. Языки XLIFF

- **Где.** `Presentation/ViewModels/PublishViewModel.cs` (экспорт `("ru", "en")`, импорт), `Core/Localization/XliffConverter.cs`,
  новый диалог выбора языков (`IDialogService.PickXliffLanguagesAsync`), реализация в `Desktop/Services`.
- **Как.** Диалог: «Исходный язык» (из `xml:lang`, можно изменить), «Целевой язык» (список + ввод кода). Нет `xml:lang` — язык интерфейса.
  Импорт читает `target-language` и сверяет с `xml:lang` документа; несовпадение — предупреждение, не отказ.
- **Проверки.** Экспорт пишет заданные `source-language`/`target-language`; без `xml:lang` — язык интерфейса; импорт с чужим
  `target-language` даёт предупреждение; существующие проверки XLIFF проходят без изменений.

### 1.5. Подписи по `xml:lang`

- **Где.** `Core/Publishing/Labels.cs` (`For(language)`), `PublishOptions.Language`, `Presentation/ViewModels/PublishViewModel.cs`,
  `Desktop/Authoring/AuthorView*.cs` (подписи в «Авторе»).
- **Как.** Метод `Labels.ForDocument(DitaDocument)`: `xml:lang` корня → язык подписей; нет — язык интерфейса. Для карты — язык
  корня карты. `PublishOptions.Language` по умолчанию остаётся языком интерфейса, но `PublishViewModel` подставляет язык карты.
- **Проверки.** Карта с `xml:lang="en-US"` собирается с «Contents»/«Note» при русском интерфейсе; без `xml:lang` — по языку интерфейса;
  `ru-RU` → русские подписи; неизвестный язык (`de`) — откат на английский.

### 2.1. Пакетный XLIFF

- **Где.** `XliffConverter` (один документ), `PublishViewModel.ExportXliff`/`ImportXliff`, `MapTree.PublicationOrder` для списка топиков.
- **Как.** Экспорт: для карты — файл `<имя>.<язык>.xliff` на топик в выбранную папку плюс `manifest.json` (соответствие путь → файл);
  импорт: выбрать папку, по манифесту применить переводы к топикам (каждый — как существующий импорт, с отчётом сегментов и
  предупреждений). Правки топиков помечаются несохранёнными, как при одиночном импорте.
- **Проверки.** Экспорт карты из 3 топиков → 3 файла и манифест; импорт возвращает изменённый текст в каждый топик; топик, которого нет
  в проекте, пропускается с предупреждением; сегменты с разметкой (`bpt/ept/ph`) не теряются; повтор импорта идемпотентен.

### 2.2. Схема категорий

- **Где.** `Core/Validation/DitaValidator.cs`, `Core/Project/DitaProject.Validation.cs` (проверка проекта), каталог `subjectScheme`.
- **Как.** При проверке проекта собрать значения из `subjectdef`/`enumerationdef` схем проекта (по `keys` и `attributedef`), для каждого
  условного атрибута топика сверить значения. Нет схемы — проверки нет (поведение прежнее).
- **Проверки.** Схема с `product = {a, b}`: топик с `product="c"` — предупреждение «значение не объявлено в схеме»; `a b` — нет
  предупреждений; без схемы — нет предупреждений; вложенные `subjectdef` и `enumerationdef` по атрибуту.

## Не берём в ближайшие этапы

| Ограничение | Почему |
|---|---|
| Коммит и push Git/SVN из редактора | Большой объём (диалог, выбор файлов, конфликты, аутентификация) и дорогая цена ошибки; отдельное решение — нужен ли |
| macOS под Apple Silicon | CefGlue не выпускает Chromium под arm64; нужен отказ от Chromium на macOS (печать PDF системным движком) — отдельный проект |
| Грамматика | Только внешними средствами (LanguageTool, сервер/API); вне встроенной проверки |
| Совместное редактирование, серверная часть | Другой продукт |
| Первое открытие большого топика ≈ 1 с | Проверить профилем; пока приемлемо |
